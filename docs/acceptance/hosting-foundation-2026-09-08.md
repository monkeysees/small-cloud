## Measurement interpretation

The first five-build run had 201 seconds of common Dockerfile execution overlap. All five completed, the sixth was refused while all five VMs existed, and all 885 serving readiness requests returned 200 (p95 6.23 ms, maximum 97.64 ms). Its separate [resource snapshots](../evidence/capacity-resources-2026-09-08.json) started after the common overlap; they are retained as post-run observations, not misrepresented as concurrent high-water measurements.

The corrected [measured run](../evidence/capacity-measured-2026-09-08.json) used five actual Dockerfiles doing four minutes of CPU hashing work each. They shared **196 seconds of execution overlap**, with 23 host resource samples inside that interval. All five completed and their VMs/addresses were deleted; the sixth request was refused. All **900 readiness requests returned 200**, p95 **6.34 ms**, maximum **98.27 ms**. Each builder consumed approximately 245–247 CPU seconds and peaked at 748–792 MiB ancestor memory; the separate pressure probes establish the harder limits. During overlap, control had at least 6.95 GiB available memory and 139.65 GiB free disk, with sampled host CPU busy at most 3.4%; runtime had at least 14.46 GiB available memory and 285.13 GiB free disk, at most 1.42% host CPU busy. Serving fixtures used 32.21–34.21 MiB each. These are lightweight readiness workloads alongside real build CPU work, not a latency guarantee for arbitrary customer applications or database saturation. Independent candidate pressure checks cover resource contention separately.

Thirty release identities share one immutable Python fixture image, deliberately deduplicated by the registry and Docker. This establishes namespace/reference/database capacity, not thirty unique maximum-size images or representative customer database growth. Worst-case storage is budgeted separately below. Five creator identities are a capacity assumption; actual membership/creator quotas remain product work. The runtime reserves five active apps plus one private, unrouted candidate for an already-active app. At the final limits, six allocations reserve 3 CPUs and 3 GiB guest memory, leaving host/gVisor headroom on the 8-vCPU/16-GiB runtime. Failed/stopped allocations still reserve their slot until explicit cleanup.

The 1 GiB `/tmp` setting is an upper mount size, not a promise of 1 GiB usable memory-backed storage under a 512 MiB total memory cap. Memory/disk/fork pressure hits memory first and kills only the candidate; a separate thread check reaches exactly 128 guest tasks. Builder memory is deliberately 3,500 MiB rather than the proposed full 4 GiB, preserving the guest OS on a 4-GB VM. Build disk exhaustion wrote 10,303,709,184 bytes before ENOSPC; task pressure reached 512 including daemon overhead; memory reached 3,670,016,000 bytes with an OOM kill. CPU observations include daemon/export overhead. The 600-second watchdog begins before daemon startup and is independent of the coordinator; the earlier retained timeout proof is not relabeled as a new permanent-session timeout run.

Network checks use known-live control listeners, a dedicated public HTTPS nonce sink and authoritative DNS. A first DNS-change attempt was invalid: it reported a private answer but performed another name lookup that could select a cached public answer. The probe now connects to the exact `getaddrinfo` record it reports; a regression test reproduces the old mismatch, and both actual Dockerfile and runtime checks were repeated successfully. Forbidden TCP/HTTP responses would fail the matrix; connection refusal to an absent listener is never treated as denial. IPv6 acceptance uses the allowed disabled alternative: host and build namespace disable flags, Docker IPv6 disabled, only loopback in the guest, and an unreachable external IPv6 attempt. No healthy external IPv6 service is claimed. Public arbitrary internet access permits creator-selected external services; it does not authorize platform management access or make this an anti-exfiltration product.

The canary VM, primary IP, dedicated firewall and temporary A/NS records were deleted; the unrelated wildcard was preserved ([cleanup evidence](../evidence/canary-cleanup-2026-09-08.json)). Renewal was forced through Caddy's renewal-window setting against the real ACME account/state, then the normal configuration was restored. Individual-host shutdowns tested independent observation and persistence, not regional failover or backup recovery.

Restarting the fixture after maintenance exposed an untagged base image removed during earlier derived-image cleanup. Docker's default image removal can recursively delete untagged parents, independently of the operator release records. Both normal cleanup and failed-preparation cleanup now use `--no-prune` without force; a regression test exercises the parent/child case. The [live corrected sweep](../evidence/parent-retention-2026-09-08.json) removed ten eligible derived images while preserving the retained untagged parent and serving containers. Reloading the exact checked archive restored the synthetic fixture; a Docker restart preserved its immutable ID. Reapplication did not change storage drivers or erase database/registry content. Operator image removal must follow the same no-parent-pruning rule.

A CX23 builder costs EUR 0.0088/hour compute plus EUR 0.0008/hour IPv4, or EUR 0.0096 per one-hour build; CPX22 fallback costs EUR 0.0312 + 0.0008 = **EUR 0.032**. One hundred CX23 builds would add EUR 0.96 instead of EUR 3.20. Ten execution minutes still incur a whole VM hour; bootstrap/export/deletion delays count in lifetime. Crossing an hour doubles that build's hourly charge. Five simultaneous CPX22 builds cost EUR 0.16 per rounded hour, and the update candidate fits the already-priced runtime. Stopped VMs continue billing. Monthly resource caps apply per VM, not across a succession of fresh builders. There is no idle prewarm cost.

Each quoted EU VM includes 20 TiB outgoing traffic; the account rate above allowance is EUR 1/TiB, with the estimator rounding usage in 100-MiB blocks. Public API traffic, downloads, registry transfer and retries still consume bandwidth; future excess is excluded from the live forecast. Local control/runtime disks are included in compute, with no paid volume, snapshot, backup or load balancer currently allocated. Resend/DNS/domain services are external to the Hetzner collector: the EUR 2 allowance is a planning allowance for the low-volume pilot using the existing domain, not an observed invoice or purchased plan. Exceeding an external free quota or adding any service requires an updated estimate; the EUR 10 contingency is not a technical limit.

Storage planning assumes at most sixty retained 500-MiB image archives (about 29.3 GiB before deduplication), plus imported/derived runtime images, five in-flight 116-MiB contexts/500-MiB exports, bounded logs, database growth and cleanup backlog. A day of 100 maximum-size build exports can temporarily add about 49 GiB plus source copies; 1,000 in one day would exceed the control disk. The ten-GiB free-space admission guard refuses new staging/build/publication under pressure; it is not an atomic reservation or a database quota. Hourly cleanup and 80%-used disk alerts need operator response. Databases have no current per-app storage ceiling, so the 160-GB control capacity is for this disposable small-board pilot, not a guarantee for arbitrary thirty-app data sizes. Product admission must retain these storage assumptions and surface capacity refusal.
