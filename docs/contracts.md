# CLI and platform contracts

These are the provider-independent pilot contracts for [implementation #3](https://github.com/monkeysees/small-cloud/issues/3), implementing [specification #1](https://github.com/monkeysees/small-cloud/issues/1). They resolve the open interfaces in [the specification](spec.md); they are requirements for subsequent implementation, not evidence of a running platform. The confirmed acceptance seam remains creator/operator CLI commands and authenticated HTTP requests.

## CLI surface

Discovery slice #30 implements resource groups and removes the old top-level paths without aliases. Bare invocation shows a starting guide. `catalog [command or group] --json` returns `data.catalog_version: 1`, a scoped command list, global inputs and the response contract; paths may be separate words or quoted. Definitions include input types, requiredness, defaults, choices, permissions, results, effects, examples and guide topics. `guide [topic]` lists or reads bundled offline guides; `--json` returns their content in the ordinary envelope. Help, catalog and guides require neither authentication nor configuration. Human app list/status output escapes terminal control characters; JSON retains the same data and versioned envelope.

The table below also retains pending lifecycle/member-removal requirements explicitly marked as pending. The catalog advertises only implemented commands. Project linking, default waiting and streaming from specification #29 remain subsequent slices; the current async contracts below describe delivered behavior. Standalone distribution and fixed-service binding are implemented in #31; split login and setup status are implemented in #32.

Implemented workspace migration (#19): existing identities and apps belong to `ws-initial`. Login and `auth status` additionally return `workspace:{id,name,owner_id}`, the service-persisted `default_workspace` ID and a separate `platform_administrator` boolean. `roles` remains the selected workspace's member/creator/administrator grants. Existing credentials require no new login or workspace prompt. Platform status does not grant workspace management or private-content access. Additional-workspace creation and explicit selection are implemented in #20; the broader multi-workspace requirements are in specification #18 and ADR 0009. See the [operator migration procedure](../identity/WORKSPACE-MIGRATION.md).

`small-cloud [global flags] <command>` publishes and manages apps from Linux or macOS without local Docker. Native Windows distribution is deferred. App names are immutable, workspace-unique lowercase ASCII slugs matching `[a-z][a-z0-9-]{0,62}`; names identify apps in commands and are never reassigned after deletion. URLs use immutable app IDs so redeployment cannot change them. Descriptions are UTF-8 text of at most 500 characters.

| Command | Inputs and result |
| --- | --- |
| `auth login` | Browser Google sign-in; `--no-browser` prints the verification URL and user code to stderr for manual opening. |
| `auth login start` | Return verification URL, human code, local attempt ID and expiry; save protected pending state without opening a browser. Supports `--json --no-input`. |
| `auth login finish ATTEMPT_ID` | Wait for approval and save the credential; `--timeout SECONDS` bounds waiting (default 600, capped by remaining lifetime). Supports `--json --no-input`. |
| `auth status` | Service endpoint, current identity, workspace, roles, credential ID, expiry, missing setup steps and next commands; never credential values. Missing sign-in remains exit 3 with setup details. |
| `auth logout` | Revoke this credential server-side, then remove local storage; already revoked is success. Offline failure retains storage so revocation can be retried. |
| `auth revoke --all` | Revoke all of the caller's CLI credentials, including this one; remove local credential after success. |
| `app deploy <folder> --name <app> [--description <text>]` | Create or update the caller's app; new apps require description (empty allowed), default creator-only. Omitted description on update preserves it. Returns deployment operation and stable URL. |
| `app check <folder>` | Offline source validation using the deploy packaging boundary, without authentication, upload, file writes or build allowance consumption. Human/JSON findings report source contents, limits and local/remote verification boundaries. |
| `app status <app>` | Current availability, active deployment, latest operation and cleanup status. Creator or administrator only. |
| `operation status <id>` / `operation status --request-id <UUID>` | Observe an accepted operation, including after a lost connection; owner or administrator only. |
| `app logs <app> --source build\|runtime` | Bounded snapshot; optional `--deployment <id>` for build logs (default latest), `--since <RFC3339>` and `--limit <1..1000>` (default 100). No streaming mode in v1. |
| `app list` | List accessible apps sorted by name, with name, description, creator and URL. |
| `app share <app> --scope creator-only\|workspace-wide` | Owner changes audience; workspace-wide with secrets requires `--acknowledge-secret-authority` or interactive acknowledgement. |
| `app secrets set <app> <name> [--stdin] [--acknowledge-secret-authority]` | Create or replace using hidden TTY prompt or stdin bytes; never an argument value. |
| `app secrets delete <app> <name>` | Delete if present; absent is successful without restart. |
| `app secrets list <app>` | Sorted secret names only. |
| Pending: `reset <app> --confirm <app>` | Erase database and initialize the current release again. |
| Pending: `delete <app> --confirm <app>` | Immediately disable access and schedule permanent cleanup. |
| `workspace create NAME --owner EMAIL` | Platform administrator creates one workspace and admits its designated owner as administrator and creator, subject to creator capacity; retry-safe with `--request-id`. |
| `workspace list` | Accessible workspace IDs, names, owner IDs, independent roles and the service-saved default. |
| `workspace select ID_OR_NAME` | Save an accessible workspace as default across CLI credentials; ambiguous names fail. |
| `workspace usage` | Workspace creator/deployed/active counts, limits and monthly build accounting. Admitted creators and administrator only. |
| `workspace member add <email>` | Administrator creates explicit pending admission for a Google-verified email; bind to Google subject on first sign-in. Existing membership is a no-op. |
| `workspace creator grant <user-id>` | Grant admitted member publishing authority within five-creator limit; existing grant is a no-op. |
| Pending: `admin member remove <user-id> --confirm <user-id>` | Revoke membership, all sessions and credentials, disable owned apps atomically. Sole administrator cannot remove themselves. |
| Pending: `admin app disable <app>` | Immediately deny access and stop runtime; repeated disable succeeds. Does not grant content access or delete data. |

No ownership transfer or re-enable command in the pilot. Disabled apps reject deployments, sharing, reset and secret mutations; owner deletion and authorized diagnostics remain possible. Member removal retains disabled apps until operator-led disposition is separately specified; it is not deletion.

Workspace targeting (#20): `--workspace ID_OR_EXACT_NAME` overrides the saved default for one command and pins it through waits. Automation must specify the immutable ID. The first admission selects a default automatically; later memberships do not change it. Inaccessible defaults require explicit reselection with `workspace list` and `workspace select`, including after fresh sign-in. Management APIs use `X-Workspace` (percent-encoded for display names). Resolved workspace identity is part of mutations and retry fingerprints; mismatched operations or app targets are rejected. Browser `/directory` uses verified Google sign-in and shows accessible apps in the selected workspace. Existing initial-workspace receipts retain their persisted format and cannot replay in another workspace. Creation accepts no workspace override. See [onboarding, API and upgrade contracts](../identity/WORKSPACES.md).

Global flags: `--json` emits the stable machine contract below; `--no-input` prohibits prompts; `--no-color` disables color. `-h/--help` works at every level without authentication and takes precedence over other arguments; `--version` reports CLI version. Respect `NO_COLOR` and `TERM=dumb`. Prompts require a TTY and are also disabled by `--json`. Missing required input fails before mutation. Normal output is readable text on stdout; progress, prompts and errors go to stderr. JSON mode emits exactly one JSON object on stdout, including failures, and only nonessential progress on stderr. No quiet/plain/verbose modes in v1. Help includes examples; completion and packaging mechanism belong to CLI implementation.

`app deploy` waits for readiness by default. Its `--no-wait` option returns acceptance only; the superseded deploy `--wait` flag is removed. `--timeout <seconds>` (positive integer, default 900) bounds observation after acceptance, excluding source validation and upload. Other network requests time out after 30 seconds. Changed secrets still return acceptance by default with optional `--wait`; their default-completion change and reset/delete CLI delivery belong to later #29 slices. Ctrl-C exits 130 within two seconds and never cancels a server operation. A disconnected or timed-out mutation may have committed: report its request ID and reconcile before submitting a new mutation.

Deployment JSON success returns `state: succeeded`, `ready: true`, the app URL and `active_deployment_id` only after the operation succeeds. Explicit immediate return gives `state: accepted`, `ready: false`; an old serving release does not establish readiness of its update. Both forms include `operation_id`, `request_id`, `workspace_id` and an exact shell-safe `next_command` for inspection. The envelope remains version 1 with additive fields. Human output names the ready app and URL or explicitly labels acceptance without confirmed readiness. Progress and periodic elapsed time go to stderr; JSON stdout contains one final envelope.

Deployment timeout (`WAIT_TIMEOUT`, exit 6) and interruption (`INTERRUPTED`, exit 130) return error details containing `request_id`, `operation_id`, `workspace_id`, last observed `state`, `work_continues: true` and `next_command`. The command is `small-cloud operation status OPERATION_ID --workspace WORKSPACE_ID --json`, pinned to the resolved workspace even if its saved default changes. Stopping observation never cancels accepted work; it can finish before subsequent inspection. When the submission response is lost or interrupted, acceptance is uncertain: details instead contain `outcome_unknown: true`, request/workspace IDs and `small-cloud operation status --request-id REQUEST_ID --workspace WORKSPACE_ID --json`. No unconfirmed operation ID is invented.

Transient network failures during observation retry only operation reads within the original deadline. If observation stops while disconnected, `last_observation_error` retains its code and safe message. Authentication or permission failures stop observation immediately with their original exit and inspection context; they do not cancel the operation. An unavailable publishing worker leaves work pending, even while authentication succeeds. No observation retry resubmits source or changes the request ID. Retrying identical source/metadata with the original request ID and workspace recovers the original operation: default mode observes its current state; `--no-wait` returns the original acceptance receipt. Changed input still conflicts.

All mutations accept `--request-id <UUID>`; CLI generates and prints one before transmission if omitted. The server retains actor-scoped deduplication records for seven days: identical operation/inputs return the original result, different inputs with the same ID return `REQUEST_CONFLICT`. A retry rechecks current authorization. Repeated deploy with a new ID builds again; repeated reset with a new ID destroys data again. Same-scope sharing and absent secret deletion are no-ops. Deletion of a tombstoned name returns its existing cleanup operation. Secret request fingerprints must not expose values. `app deploy --dry-run` validates and reports included/excluded relative paths and total bytes locally, without uploading, reserving quota or claiming server feasibility. There is no `--force` bypass for confirmation.

The distributed CLI always uses `https://small-cloud.monkeysees.one` under ADR 0010. There is no endpoint flag, environment override or configuration loader; previous endpoint environment variables and user configuration are ignored. No repository config or automatic `.env` loading occurs. Existing credentials for this exact origin retain their storage location and remain usable; credentials for another origin are never selected or migrated. Redirects remain refused. Internal HTTPS tests use a source-only launcher or a separately built fixture executable; neither launcher is shipped in the release. Standalone executables bundle Python for Linux and macOS, ARM64 and x86-64; see [distribution](../distribution/README.md) for platform requirements and installation. Installation never initiates login or edits shell startup files.

## Machine output and states

The unreleased product contract uses `app`, `deployed_apps`, `active_apps` and `APP_DISABLED`. Existing operator-infrastructure records have a separate [compatibility boundary](../infra/README.md#build-and-runtime-operations); they do not define product response fields.

Every response has `schema_version: 1`, `ok` (boolean), `request_id` (UUID or null for local reads/errors), `data` (object or null), and `error` (object or null). Unknown additive fields must be ignored; incompatible changes require a schema version change. Timestamps are UTC RFC3339; durations and byte counts are integers. IDs are opaque strings. No secret values, database connection URLs, credentials or raw provider errors appear in output.

```json
{"schema_version":1,"ok":true,"request_id":"bc517a70-2f61-4da0-bd90-41c1e4216940","data":{"operation_id":"op_123","request_id":"bc517a70-2f61-4da0-bd90-41c1e4216940","workspace_id":"ws-initial","state":"succeeded","ready":true,"app":"check-in","url":"https://app-example.invalid","active_deployment_id":"op_123","next_command":"small-cloud operation status op_123 --workspace ws-initial --json"},"error":null}
```

```json
{"schema_version":1,"ok":false,"request_id":null,"data":null,"error":{"code":"CONFIRMATION_REQUIRED","message":"Confirm check-in; its data cannot be recovered.","retryable":false,"details":{"app":"check-in"}}}
```

Errors always include `code`, safe human `message`, `retryable` and object `details`. Details may include `operation_id`, `retry_after_seconds`, limits or validation field; messages are not a parsing contract.

| Exit | Stable error codes | Meaning |
| --- | --- | --- |
| 0 | none | Read succeeded, mutation accepted, or waited operation succeeded. |
| 1 | `INTERNAL`, `BUILD_FAILED`, `STARTUP_FAILED`, `RESET_FAILED`, `CLEANUP_FAILED` | Platform or terminal operation failure. |
| 2 | `INVALID_ARGUMENT`, `CONFIRMATION_REQUIRED`, `CONFIRMATION_MISMATCH`, `ACKNOWLEDGEMENT_REQUIRED`, `UPLOAD_REJECTED` | Local or server input validation; no mutation. |
| 3 | `AUTH_REQUIRED`, `CREDENTIAL_REVOKED`, `LOGIN_EXPIRED` | Sign in again. |
| 4 | `FORBIDDEN`, `NOT_FOUND`, `APP_DISABLED` | Permission, hidden/missing resource or disabled state. Unauthorized resource queries return `NOT_FOUND`. |
| 5 | `BUILD_BUSY`, `ALLOWANCE_EXHAUSTED`, `ALLOWANCE_RESERVED`, `CREATOR_CAPACITY`, `DEPLOYED_CAPACITY`, `ACTIVE_CAPACITY`, `OPERATION_CONFLICT`, `REQUEST_CONFLICT` | Conflict or quota refusal; admission refusals create no mutation. Accepted operations can subsequently fail on active capacity as described below. |
| 6 | `NETWORK_ERROR`, `WAIT_TIMEOUT` | Outcome may be pending/unknown; reconcile using request/operation ID. |
| 130 | `INTERRUPTED` | Local interruption; accepted work continues. |

Operation records contain `id`, `kind` (`deploy`, `secret-change`, `reset`, `delete`), `app`, `state`, `created_at`, `updated_at`, nullable `completed_at`, and nullable `error`. States are `accepted`, `building`, `starting`, `cleaning`, `succeeded`, `failed`; only applicable phases occur. Delete cleanup failure additionally exposes retries below and can later reach success. Reads of failed operations exit 0 with the failure in data; waiting for completion returns the failure exit. Deployment terminal errors retain the operation's code, message and details, plus inspection context, `state: failed` and `work_continues: false`. App status contains `app`, `url`, `sharing_scope`, `availability` (`starting`, `running`, `stopped`, `unavailable`, `disabled`, `deleting`, `deleted`), nullable `active_deployment_id`, nullable latest operation record and nullable cleanup record. Failed updates never overwrite the active deployment ID.

`workspace usage` returns `creators`, `deployed_apps`, `active_apps` as `{used,limit}`, and `build` as `{period_start,period_end,limit_seconds,charged_seconds,reserved_seconds,available_seconds}`. Auth results contain `user:{id,name,email}`, `roles`, `credential_id`, `expires_at`; logout/revoke return `{revoked:true}`. Secret list returns `{names:[]}`. Sharing returns `{app,sharing_scope,secret_authority_acknowledged}`. Admin writes return affected user/app ID and resulting membership/creator/disabled state. Logs return `{entries:[{timestamp,source,deployment_id,message}],truncated,dropped_bytes,oldest_available_at,next_cursor}`; `--cursor <opaque>` continues a snapshot, mutually exclusive with `--since`. Expired cursors yield `INVALID_ARGUMENT`. Dry run returns `{included:[],excluded:[],total_bytes}`. These are fields of `data`, not separate envelopes.

## Browser login, credentials and request identity

Login creates a ten-minute, single-use pending session over HTTPS with a random poll secret and human verification code. Combined `auth login` starts, presents approval and waits; split `auth login start` returns `verification_url`, `user_code`, independent random `attempt_id`, `expires_in` seconds and UTC `expires_at`. The poll secret is never displayed or used as the attempt ID. It is saved with its exact service origin and expiry in a 0600, single-link file under the existing protected 0700 per-user state directory outside source folders. Origin mismatch, unsafe permissions, symlinks and hardlinks are refused. Start never opens a browser.

`auth login finish ATTEMPT_ID` runs as the same OS user on the same machine, reads protected pending state under the credential lock, polls at five-second intervals honoring server backoff, and saves the one-time credential using the existing OS-store/file rules. Successful delivery and observed expiry delete pending state. A locally unknown or consumed attempt returns `LOGIN_EXPIRED`; invalid identifiers fail before polling. Abandoned local files may be deleted; the server expires their authority after ten minutes. Timeout (`WAIT_TIMEOUT`, exit 6), interruption (`INTERRUPTED`, exit 130) and network failures preserve pending state and return `attempt_id` and `next_command` in error details. Lost one-time delivery requires a fresh start. A failed credential save preserves the storage error, attempts server-side revocation and directs a fresh login; `credential_revocation` reports `revoked` or `unconfirmed`. Unconfirmed revocation includes instructions to sign in again and revoke all CLI credentials. `--no-input`, JSON and non-TTY execution prohibit terminal prompts but permit explicitly initiated human browser approval. `--no-browser` on combined login permits manual browser use without a local callback.

Successful login and status add `service_endpoint`, `missing_steps` and `next_steps` to the existing identity/workspace metadata. Status without a usable credential retains `AUTH_REQUIRED` or `CREDENTIAL_REVOKED` and exit 3, with service endpoint, null `user`/`workspace`, missing steps and a login-start command in error details. Service/access errors retain their distinct code and repair guidance. Members can list apps; publishing requires a separate creator grant. Available workspace context is the existing initial workspace and saved default; richer selection remains #20.

The platform performs Google authorization-code sign-in with state, nonce and PKCE, validates issuer, audience, signature and expiry, and requires verified email plus explicit admission. The browser displays the requested CLI login and user code for approval. Repeated verified sign-in to the same account retains an existing valid management session without extending its expiry, so multiple open approval forms remain usable. A different account or an expired/unknown session receives a new session; stale forms from a previous account cannot approve under the new identity. Pending admission is atomically bound to Google's issuer/subject; subsequent email changes cannot change account ownership. The platform maps this subject to an immutable random user ID. Name/email are current profile attributes, not authorization identifiers. Successful polling delivers a random, revocable platform credential once; Google tokens are never given to the CLI or an app.

Credentials expire after 30 days without automatic renewal. Store the credential in the OS credential store where available; otherwise an owner-only file under `$XDG_STATE_HOME/small-cloud` (default `~/.local/state/small-cloud`, directory 0700/file 0600). Reject symlinked or unsafe storage. Do not accept platform tokens through flags, environment variables or project files. The server stores only a verifier; check credential validity and current membership/role on every management request. Browser sessions have a 12-hour maximum and immediate server-side revocation on removal. Secure, HttpOnly browser cookies use SameSite=Lax and state-changing platform requests require CSRF protection. App and management origins must be separated with host-only cookies; apps never receive platform cookies or CLI bearer tokens.

The gateway authorizes every app route and method before forwarding, including assets and upgrade requests. Unauthenticated browser navigation redirects to login; other unauthenticated HTTP requests return 401. Unadmitted users receive 403; unauthorized app access receives 404. Administrator diagnostics/disable permissions do not grant creator-only content access. Scope changes/removal/disable affect every subsequent request and terminate existing upgraded/streaming connections; already completed responses cannot be recalled.

After authorization the gateway strips all incoming `X-Small-Cloud-*` headers case-insensitively (including duplicates), then writes exactly one each of `X-Small-Cloud-User-ID`, `X-Small-Cloud-User-Name`, and `X-Small-Cloud-User-Email`. ID is ASCII; name and email are unpadded base64url UTF-8, avoiding header injection and Unicode ambiguity. It strips platform authentication material before forwarding. Runtime ingress accepts only authenticated gateway traffic, bound to the intended app; other apps and public routes cannot impersonate the gateway. Apps may trust these headers only on this protected ingress. Provider mechanism (for example authenticated private ingress) must be proven at the hosting gate; headers alone are insufficient. Internal readiness probes carry no invented user identity and have no public bypass route.

## Source and runtime

App preparation (#33): `guide runtime` bundles the runtime contract, source exclusions and repair instructions offline. `app check FOLDER` requires no app name, workspace, credentials or Docker. It uses the existing deploy packager and archive validator, reads source into memory, writes no files, makes no service requests and consumes no build allowance. `--workspace` and `--request-id` have no effect; the result's `request_id` is null. Human results escape control characters in paths. JSON success returns `data:{summary,included,excluded,total_bytes,limits:{max_bytes,max_files},source_rules,verified_locally,requires_remote}`. Paths are relative, excluded directory entries include their descendants, and file contents are never returned. Limits are 104857600 uncompressed file bytes and 10000 included files. Locally verified requirements cover root Dockerfile presence, safe reads and archive validation; Dockerfile syntax/COPY inputs, dependencies, HTTP readiness, database initialization, runtime compatibility and server admission remain unverified. The summary explicitly disclaims remote feasibility and readiness, and deploy revalidates source. Failed checking stops at the first source-validation error and returns `UPLOAD_REJECTED` (exit 2), null data and details containing limits, `next_command:"small-cloud guide runtime"` and repair/recheck `next_steps`; it never reports a partial manifest as valid. No starter files are generated and no stack is prescribed.

Build context is the selected folder, with a required root `Dockerfile`. Apply root `.dockerignore` using Docker pattern semantics, then mandatory exclusions that negation cannot override: every `.git` directory, every `.env` and `.env.*` file, `.small-cloud` directories, and platform config/credential directories and files. Reject uploads whose source root contains or is inside a configured platform credential/config directory; check canonical paths and file identities, including hardlinks. Reject symlinks, special files, absolute/traversing archive entries and files changing during packaging; package from the validated file handles. The server independently validates archive paths/types, exclusion rules and extracted size. Limit context to 100 MiB uncompressed and 10,000 files. Dry run shows exclusions; creators remain responsible for other embedded credentials. Builds never receive runtime secrets, CLI credentials or database credentials. No private dependency authentication or extra build contexts in v1.

The container runs unprivileged, listens on `0.0.0.0:$PORT` and receives `DATABASE_URL`; their values are platform-owned. Engine/version, CPU architecture, CPU/memory/disk limits and provider are unresolved hosting-gate choices. Apps expose `GET /_small-cloud/ready`, returning 200 only after repeatable initialization; the gateway reserves this path from public access. Readiness must succeed within 120 seconds after start request; poll every two seconds with a one-second request timeout. Container filesystems and memory are temporary; only the database survives normal lifecycle operations.

Reserve active slots atomically, counting starting apps. At five slots, cold starts fail immediately with HTTP 503 `ACTIVE_CAPACITY` and a visible retry control. Starting apps return HTTP 503 `STARTING`, `Retry-After: 2` and a loading page for HTML clients. Do not replay a POST automatically: users retry after readiness. Startup failure releases its reservation and shows HTTP 503 `STARTUP_FAILED` with retry. Thirty minutes without an authorized forwarded HTTP request stops an app; internal probes and denied requests do not reset the timer. An in-flight request prevents idle stop; upgraded connections count as active until closed.

The implemented [idle lifecycle](../identity/LIFECYCLE.md) includes queued starts and unconfirmed cleanup in active usage. Request completion starts a fresh idle window; protocol upgrades remain unsupported. HTML GET loading pages refresh every two seconds; failures require an authenticated `GET /_small-cloud/retry?return=PATH` before another attempt. Success redirects to the same app origin with HTTP 303. Status adds nullable `runtime_error`; `reconciliation_required` retains the reservation until confirmed cleanup. The independent lifecycle worker serializes starts, and readiness allows 120 seconds after runtime launch. Existing running apps receive a fresh idle window when the lifecycle schema is first installed.

Deploy first builds, then starts a candidate and switches routing only after readiness. Failed build/startup removes the candidate, records failure and leaves the prior container and database in place. First-deploy failure leaves an unavailable app that can be retried or deleted. A first deploy or update of a stopped app reserves an active slot after building. If none is available, the accepted deployment operation becomes `failed` with `ACTIVE_CAPACITY`; the build remains charged, the candidate is cleaned, and any previous deployment stays unchanged. Default deployment observation exits 5 for this terminal failure; the creator can redeploy when capacity is free. Updating an active app may temporarily run its old and candidate containers within the same app slot; hosting must budget this overlap without exceeding five active apps. Serialize deploy/reset/secret changes per app; conflicts fail immediately. Delete or administrator disable fences/cancels pending work so later completion cannot re-enable it.

Secret names match `[A-Z_][A-Z0-9_]{0,127}`; reserve `PORT`, `DATABASE_URL` and `SMALL_CLOUD_*`. Values are 1–16,384 UTF-8 bytes excluding NUL; stdin preserves trailing newlines and is read only with `--stdin`, bounded before submission. Limit 50 names per app. Persist encrypted changes atomically, stop the old runtime, then restart with the saved configuration (including previously stopped apps, subject to active capacity). Reject a stopped app's secret mutation before saving when no slot is available. Failure after saving leaves the new configuration saved and the app unavailable; never silently roll back to old credentials. On-demand retry uses saved configuration. Report `STARTUP_FAILED` with `configuration_saved:true` and operation ID. Setting secrets on an already shared app also requires the same authority acknowledgement as sharing a secret-bearing app.

## Build allowance and logs

A calendar month is `[00:00:00 UTC on day 1, next month)` with 60,000 seconds shared allowance. At build admission atomically acquire the creator's single-build lock, a new-app deployed slot if needed (30 including pending first deploys), and reserve 600 seconds from that month's available allowance. No queue: conflicts fail immediately. If available is below 600 seconds, return `ALLOWANCE_RESERVED` when unsettled reservations could restore 600, otherwise `ALLOWANCE_EXHAUSTED`, including charged/reserved/available counts. This conservative admission rule can leave fewer than ten usable minutes unspent and must be visible in usage/help.

Charge elapsed isolated build execution from worker start (including dependency download/image export) to confirmed worker termination, rounded up once to whole seconds, maximum 600; no charge for upload, scheduling, runtime startup or a build that never starts. Failed/cancelled/timed-out builds consume actual execution seconds. Enforce termination at 600 seconds. Keep the reservation and creator lock until termination is confirmed; uncertain worker state cannot release capacity optimistically. Record and expose reconciliation failures to the administrator. Settle exactly once, release unused reservation, and prevent charged plus reserved exceeding 60,000. A build crossing midnight remains wholly in its admission month's ledger; new month starts with zero charges/reservations except its own admissions. The per-creator lock crosses month boundaries. Running apps are unaffected by allowance exhaustion.

Retain logs for seven days from ingestion. Store at most 10 MiB per build and 50 MiB runtime logs per app across deployments; evict oldest complete records on overflow. Each stored record is at most 16 KiB UTF-8, marked if shortened. Bounds include encoded record metadata. Redact before persistence and truncation, including values split across input chunks; buffer sufficiently for maximum secret length. Redact known app secret values, database URL/password and any platform credentials accidentally present in captured platform diagnostics. Keep replaced/deleted values encrypted in a redaction-only set for seven days after their last possible runtime use, inaccessible through secret APIs. Full deletion removes this set with logs. Literal redaction cannot prevent deliberate encoding or other disclosure by app code.

Log snapshots are at most 1 MiB and 1,000 entries. `truncated`, `dropped_bytes` and `oldest_available_at` expose record shortening, volume/age loss and pagination limits; continuation cursor distinguishes more available records from permanent loss. Escape terminal controls in human output; JSON encodes them as data. No unbounded debug archive is allowed. Hosting must cost these bounds and at most current plus candidate/previous release artifacts; superseded/failed artifacts and uploaded source are cleaned within 24 hours after deployment finishes, excluding artifacts still serving the active release.

Implemented diagnostics (#11) additionally report `collection_interrupted` for possible unmeasurable loss; this sets `truncated` without inventing a dropped-byte count. Cursors are actor/app/source-bound, expire after ten minutes, and continue the original build despite redeployment. Runtime records may split or combine while redaction holds a possible secret prefix. See [collection, upgrade and retention details](../identity/DIAGNOSTICS.md).

## Reset, deletion and failure visibility

Interactive reset/delete prints the exact immutable name and “Data cannot be recovered” and requires typing it. Noninteractive commands require `--confirm` with the exact case-sensitive name; IDs, yes/no and `--force` are not substitutes. Confirmation and owner authorization are checked server-side against the target before any effect. For reset, reserve an active slot before any erasure (reuse its slot if active; fail without mutation if full), then stop traffic/runtime, erase and recreate the logical database with scoped credentials, then start the current code. Retain URL, code, secrets and sharing. Reset has a ten-minute completion deadline; failure leaves the app unavailable with `RESET_FAILED`, safe diagnostic reason and whether erasure completed. Retry with the same request ID observes the old result; a newly confirmed reset can retry the work. Database changes are never rolled back automatically, including failed deployment migrations.

Deletion acknowledges only after an access-denial tombstone and cleanup job are durable. Revoke database access, stop runtime and deny directory/app access immediately; unavailable workers do not postpone gateway denial. Cleanup must remove uploaded source, unreferenced container/image artifacts, database, secrets/redaction material and logs within 24 hours of acceptance. Shared image layers may remain only while referenced by another live release. Retry failures after 1, 5, 15 and 60 minutes, then hourly; retries are idempotent and never restore access. At 24 hours mark `failed`, alert the administrator and continue hourly retries until removal is verified. Deadline is an operational requirement, not a silent promise despite provider failure.

Owner and administrator can read the tombstone/status after deletion; removed owners cannot. Cleanup status includes `state` (`pending`, `retrying`, `failed`, `complete`), `deadline_at`, `attempts`, `next_retry_at`, safe `last_error`, and per-resource removal results. Permanent lightweight tombstones retain only app ID/name, owner ID, timestamps and completion state; detailed cleanup diagnostics expire seven days after completion. Deployed capacity is released only after cleanup completes, so pending or failed deletion cannot bypass storage limits. Disable alone does not release deployed capacity.
