# Idle apps and active capacity

Apps stop after 30 minutes without an authorized HTTP request forwarded to app code. An in-flight request prevents stopping; its completion begins a fresh idle window. Internal readiness probes, sign-in, directory/status/log reads, denied requests and rejected request framing do not keep an app active. The worker checks once per second when free. An ongoing deployment keeps its app running until the deployment finishes; lifecycle work runs separately from builds. Protocol upgrades remain unsupported.

Stopping removes the container and frees its active slot. The selected release, URL, sharing scope and app database stay intact. The next authorized app request reserves a slot and asks the lifecycle worker to launch the retained image with the same database credentials. No rebuild or build allowance is required. Database initialization must remain repeatable. Temporary filesystem contents and in-memory state can disappear on every stop/start; the database remains disposable, with no backup or recovery guarantee.

There are five active slots in the initial workspace and installation. Running, queued and starting apps reserve slots; unconfirmed cleanup also retains its reservation. A sixth start immediately receives HTTP 503 `ACTIVE_CAPACITY` and an HTML capacity message with a **Retry** button. The platform never evicts an actively used app to admit another. Retry after an idle app stops. Publication startup shares this reservation boundary; updating an active app keeps its existing slot and the runtime's single replacement-candidate allowance.

While starting, requests receive HTTP 503 `STARTING` and `Retry-After: 2`. HTML GET requests see a loading page that refreshes the requested URL every two seconds. Startup is serialized by the lifecycle worker, so another app's startup can add a delay; after launch, readiness has a 120-second deadline. Capacity refusals and startup failures do not automatically refresh. POSTs and other mutations are never automatically replayed: wait for readiness, then deliberately submit the change again.

A failed start returns HTTP 503 `STARTUP_FAILED`. After successful cleanup its slot is released. Use the page's **Retry** button, or send an authenticated GET to `/_small-cloud/retry?return=%2F` to explicitly retry the saved release. An ordinary request continues to report failure until this explicit retry. The `return` parameter selects a path on the same app origin; successful retry redirects there with HTTP 303. The route remains authenticated and subject to the app's sharing scope. A browser can finish Google sign-in while its app is stopped or capacity is full.

`small-cloud status APP` reports `running`, `stopped`, `starting` or `unavailable` alongside the unchanged selected deployment. `runtime_error` contains a safe runtime failure, including `reconciliation_required` when cleanup is uncertain. `small-cloud usage` includes pending starts and uncertain cleanup in the active count. Deployment and lifecycle operations on the same app cannot overlap; retry a conflicting deployment after startup/cleanup finishes.

## Operator installation and recovery

Install the updated `infra/runtime/sandbox.py` on the runtime host before enabling lifecycle operation. Its `stop APP` command removes only that app's active allocation and refuses a replacement candidate; it retains database resources and release-image references. `resume APP DEPLOYMENT --env-file FILE` resolves the immutable retained release and uses the normal sandbox launch path, including network policy, resource limits, capacity and diagnostics. The lifecycle worker decrypts existing database credentials on the control host and removes its root-only temporary environment file after use.

Stop the publishing worker during the code upgrade, restart identity to migrate SQLite, then restart publishing. Existing running apps receive a fresh 30-minute idle window on the first migration. Install [small-cloud-lifecycle.service](small-cloud-lifecycle.service), run `systemctl daemon-reload`, and enable/start `small-cloud-lifecycle`. It uses the existing root-owned `/etc/small-cloud/publishing.json` and runs independently of `small-cloud-publishing`. Do not run a second lifecycle worker outside its process lock.

Kernel locks shared with ingress prevent stopping in-flight requests and release automatically on process exit. Queued starts survive control-service restart. After lifecycle-worker interruption, it removes any uncertain started allocation before freeing the slot; the retained release remains available for another request. If runtime access or cleanup fails, status reports `reconciliation_required` and the reservation stays held. Restore runtime connectivity, inspect the reported app and restart `small-cloud-lifecycle` to retry its scoped cleanup. Do not free reservations manually while an allocation might remain. A runtime-host reboot still requires operator reconciliation of previously running apps under the existing hosting contract.

## Verification

Run `python -m unittest identity.tests.test_lifecycle_http` with the repository's installed dependencies for deterministic authenticated request timing, in-flight protection, competing starts, capacity retry, publication capacity, failed startup and restart/cleanup recovery. `identity.tests.test_database_http.DatabaseAcceptance.test_http_idle_threshold_and_on_demand_start_preserve_database` runs the real starter against disposable PostgreSQL through CLI and authenticated HTTP. The deployment and runtime CLI tests exercise the operator handoff with controlled external processes. These are local checks; they do not establish deployed EU acceptance or browser-rendering evidence.

Local verification on 2026-09-09 passed 72 identity tests, 88 infrastructure CLI tests and 4 hosting-fixture tests (164 total), plus Pyright 1.1.413 with zero errors. Standards and Spec reviews had no remaining findings after correcting cold-start framing validation.

The [hosted acceptance report](../docs/acceptance/app-lifecycle-2026-09-09.md) records deployment, an untouched 30-minute idle interval, competing starts, persistence, failure/restart recovery and cleanup. Live HTTP/CLI checks passed. The operator accepted closure on 2026-09-09 assuming the remaining browser checks pass; rendered-browser verification was not performed.
